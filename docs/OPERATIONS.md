# JP Bids MCP 運用手順

対象: Public版0.10.0 / 更新日: 2026-10-21 JST

この手順は運営担当者向けです。[使用説明書](./USER_GUIDE.ja.md)と[検証状況](./VERIFICATION_STATUS.md)を公開案内の基準とします。認証情報・内部管理画面・非公開の運用ログは本書に保存しません。

## 担当と正本

- 運営担当は、問い合わせ受付、既知の問題、公開ページの検証状況を管理します。
- 開発担当は、対象コミット・CI結果と機能仕様の変更を記録します。
- 告知担当は、承認済み文面、投稿先、実行時刻、投稿結果を管理します。
- README、紹介ページ、Zennは入口です。詳細手順はUSER_GUIDE、機能契約はFUNCTIONAL_SPEC、確認範囲はVERIFICATION_STATUSを正本とします。
- 担当者と受付時間帯は運営側で設定します。未設定の24時間対応や回答時間を約束しません。

## 公開前と告知当日

1. 公開資料の接続URL、料金、検証日、確認範囲が整合していることを確認します。
2. 予約記事を修正するときは、公開日時・公開状態を保持した差分か確認します。予定日時を過ぎていないかも確認します。
3. X告知は承認済みJSONの本文をそのまま使います。JSONの保存は自動投稿予約を意味しません。
4. 実行開始時刻以降、記事のタイトルと本文が一般閲覧できることを確認します。HTTP 200だけでは、認証画面でないことの確認になりません。
5. 通常のアカウント取得機能で、承認済みの投稿先と一致することを確認します。
6. 1投稿目を送信し、成功応答の実際の投稿IDを保存します。2投稿目はそのIDへの返信にします。ユーザーIDを返信先に使用しません。
7. 投稿URL、返信関係、時刻、成否を記録します。

エラー、タイムアウト、応答不明の場合は再送しません。読み取りで投稿の有無を確認してから対応を決めます。1投稿目だけが成功した場合に、1投稿目から作り直すことはしません。正本が既知の場所にある場合、PC全体・認証情報・クリップボードの探索は不要です。

## 問い合わせの一次対応

通常の技術的不具合は[GitHub Issues](https://github.com/SUGUKURU-CO-LTD/jp-bids-mcp/issues)、公開できない情報を含む相談は[会社の問い合わせ窓口](https://sugu-kuru.co.jp/contact)の受付方法を確認して案内します。

記録する項目は、日時、クライアント、接続先、対象版、操作、成否、取得件数、確認できるリクエストID、秘密情報を除いたエラーです。アクセストークン、認可コード、Cookie、署名付きbid_refは公開ログから除きます。

| 症状 | 最初に確認すること | 対応 |
| --- | --- | --- |
| 接続・認証失敗 | 正規URL、会話内の有効化、クライアントの組織権限、エラー | 認証を連打しない。原因と影響範囲を確認 |
| 検索失敗・タイムアウト | 上流応答、対象条件、確認可能なリクエスト情報 | 大量の再試行を避け、利用者へ状況を案内 |
| CSV行の不整合 | 元CSV、選択状態、案件Key、機関・理由、取得経路 | 問題のCSVの利用を止め、固定データで再現を調べる |
| 保存・コピー失敗 | 通知文、ホスト機能、実際の取得物 | チャット依頼・操作文コピーをCSV取得完了と混同しない |
| 参照期限切れ | 応答エラーと古い検索結果の利用 | 通常利用では利用者の意思で再検索。制約付き検証では停止条件を優先 |

CSV不整合の原因を、生応答の比較なしにAIの転記やサーバーの問題へ断定しません。元ファイル、ツールの生応答、チャットで再提示されたテキストを別の証拠として扱います。

HTTP件数は確認できる実通信ログから集計し、ツール呼出数から推定しません。証拠がない過去の累計は未確定として保持します。

## 配備と復旧

製品MCP、企業サイト、Zennは別の配布経路です。

- README等の文書変更だけで、製品MCPの再デプロイやnpm再公開を行いません。
- 対象サービス・プロジェクト、ソースコミット、配備リビジョン、イメージdigest、復旧先を対応付けて記録します。GitHubのmain更新を本番配備完了と扱いません。
- 企業サイトの配布ソースがGitHubに未同期の場合は、その事実と保管先を運営記録に残し、リモート履歴との同期を回復します。
- 障害の影響を受ける機能の案内を見直し、利用可能な範囲を示します。承認済みの復旧手順と対象を確認してから変更します。
- 監視・コスト上限・通知先・ログ保持・復旧担当の実設定は別途確認します。本書の作成を、これらの設定完了とは扱いません。

## 文書変更の検査

READMEを修正したら `npm run docs:api` で生成API文書を更新します。差分をレビューし、コミット対象に含めます。コミット後の `npm run docs:check` と既存CIで生成物の整合を確認します。

文書だけの変更に、実KKJへの再検索や新しい回帰テストは必須としません。製品コードが変わる場合は、その変更に対応するテストと実行範囲を別途決めます。企業サイトは既存ビルドと変更箇所の表示確認を行います。
